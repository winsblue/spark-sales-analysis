## 1. 数据来源

### 1.1 两套数据源（设计说明）

本项目**同时支持两套数据源**，跑的是同一套代码、同一套清洗与统计逻辑：

| | **真实数据集（主用）** | **模拟数据集（对照）** |
| --- | --- | --- |
| 来源 | Olist 巴西电商公开数据集（真实商业数据） | 本项目生成器程序化生成 |
| 订单明细 | 102,425 行 | 200,177 行 |
| 时间跨度 | 2016-09 ~ 2018-10（真实日期） | 2026-06 ~ 2026-08（虚构日期） |
| 货币单位 | **巴西雷亚尔（BRL）** | 人民币（元） |
| 数据质量得分 | 1.0000（发布方已清洗） | 0.9645（主动注入 8 类脏数据） |
| 维度完整性 | 缺"渠道""品牌""折扣"（源数据限制） | 7 个维度全部完整 |
| 用来验证什么 | **真实业务口径、多维分析、服务化** | **清洗规则、数据质量治理能力** |

**为什么要保留两套？** 两者能证明的能力不同：

1. **真实数据集**证明"面对真实业务数据能不能算对、能不能讲出业务结论"——
   GMV、客单价、类目排名、地域分布均与 Olist 公开统计一致；
2. **模拟数据集**证明"面对脏数据能不能治理"——真实公开数据集是发布方清洗过的
   （实测 8 条规则只命中 1 条），只有在主动注入脏数据的场景下，
   清洗规则、留痕机制、数据质量得分才有意义。

> 关键在于：**切换数据源不需要改任何一行代码**，只改 `data.raw.dir` 配置即可 ——
> 这本身就说明数据接入层与业务逻辑是解耦的。

### 1.2 真实数据集：Olist 巴西电商公开数据集

#### 来源与概况

- **名称**：Brazilian E-Commerce Public Dataset by Olist
- **内容**：巴西最大电商平台之一 Olist 的 **10 万笔真实订单**（2016-09-04 ~ 2018-10-17），
  覆盖订单、商品、客户、支付等多维度，数据已做匿名化处理
- **获取方式**：项目提供一键下载脚本（走 jsDelivr CDN，国内可直连、无需代理）

```bash
# Windows
powershell -ExecutionPolicy Bypass -File scripts\download-real-data.ps1
# Linux
scripts/linux/download-real-data.sh
```

#### 原始表与规模（实测）

| 原始文件 | 行数 | 关键字段 |
| --- | --- | --- |
| `olist_orders_dataset.csv` | 99,441 | 订单状态、下单时间、各节点时间 |
| `olist_order_items_dataset.csv` | 112,650 | 商品、卖家、单价、运费 |
| `olist_customers_dataset.csv` | 99,441 | 客户唯一 ID、城市、州 |
| `olist_products_dataset.csv` | 32,951 | 商品类目（葡萄牙语） |
| `olist_order_payments_dataset.csv` | 103,886 | 支付方式、支付金额 |
| `product_category_name_translation.csv` | 71 | 类目葡语 → 英文 |

#### 转换为本项目 ODS 格式（字段映射）

本项目不直接消费这 6 张表，而是先经过**适配层**（`com.sales.generator.RealDataImporter`）
转换为与模拟数据**完全同构**的 ODS 标准格式，因此下游清洗 / 统计 / 落库代码零改动：

| 本项目 ODS 字段 | Olist 来源 | 说明 |
| --- | --- | --- |
| `order_id` | orders.order_id | 直接映射 |
| `order_time` | orders.order_purchase_timestamp | 下单时间 |
| `user_id` | customers.**customer_unique_id** | 用**真实用户 ID**（96,096 个，存在复购），而非每单唯一的 customer_id |
| `product_id` | order_items.product_id | 直接映射 |
| `channel` | —— **源数据无此字段** | 固定填 "Olist商城"（该数据集为单渠道市场） |
| `province` | customers.customer_state | 巴西 27 个州 |
| `city` | customers.customer_city | 4,119 个城市 |
| `quantity` | order_items 行数聚合 | 同一订单同一商品多行即多件 |
| `unit_price` | order_items.price | 单价（不含运费） |
| `discount_amount` | —— 源数据无此字段 | 固定 0.00（Olist 的 price 已是成交价） |
| `pay_amount` | price × quantity | 实付金额；**运费 freight_value 不计入**（口径见下） |
| `order_status` | orders.order_status | 英文状态映射为中文，见下表 |
| `pay_type` | order_payments.payment_type | 一单多笔支付时取金额最大的一笔 |

**订单状态映射**（决定"有效订单"口径）：

| Olist 原始状态 | 映射为 | 计入有效订单 |
| --- | --- | --- |
| `delivered` | 已完成 | ✅ |
| `shipped` / `invoiced` / `processing` / `created` / `approved` | 已支付（已付款成功、尚未完成） | ✅ |
| `canceled` | 已取消 | ❌ |
| `unavailable`（无法履约，实际会退款） | 已退款 | ❌ |

**支付方式映射**：`credit_card`→信用卡、`debit_card`→借记卡、`boleto`→Boleto票据、
`voucher`→代金券、`not_defined`→未知。

**类目编码**：Olist 只提供类目名（英文翻译后最长 45 字符，超过 `category_id` 列宽 32），
因此适配层按名称排序生成稳定的可读编码 `CAT001`、`CAT002`…（共 74 个），
类目名单独存入 `category_name`。

#### 金额口径说明（重要）

- **货币单位是巴西雷亚尔（BRL）**，不是人民币。项目通过配置统一控制：
  `spark-job.properties` 的 `data.currency.unit=BRL` 与 `application.yml` 的 `app.currency.unit: BRL`；
- **GMV 只统计商品成交额，不含运费**（`freight_value`）。原因是金额一致性校验规则 R06
  要求 `实付金额 = 数量 × 单价 − 优惠`，若把运费计入实付会与公式冲突。
  运费字段可作为后续扩展（如"运费率"指标）使用。

#### 真实数据的质量观察（实测）

转换后共 **102,425 行明细**，跑完整套清洗规则的结果：

| 规则 | 命中 | 说明 |
| --- | --- | --- |
| R01 空值填充 | **1** | 有 1 个订单在支付表中无记录，支付方式被填充为"未知" |
| R02 重复记录 | 0 | 发布方已去重 |
| R03 时间异常 | 0 | 时间格式统一、无非法值 |
| R04~R06 金额异常 | 0 | `数量 × 单价 = 实付` 100% 成立 |
| R07 状态非法 | 0 | 状态值均已知（适配层已映射完毕） |
| R08 维度缺失 | 0 | 商品维度覆盖率 100% |
| **数据质量得分** | **1.0000** | 真实公开数据集是已清洗过的 |

> **这个结果本身就是一条结论**：真实公开数据集的"干净"是发布方治理过的结果；
> 清洗规则真正的价值要面对原始脏数据才体现得出来 ——
> 这正是保留模拟数据源作为对照的原因。

### 1.3 模拟数据集（对照用）

本项目为实训项目，同时保留**程序化模拟生成**的数据集作为对照。
生成器 `com.sales.generator.MockDataGenerator` 按电商平台的真实业务分布特征生成数据，
并**按比例主动注入 8 类脏数据**（对应 8 条清洗规则）：

- **商品维度**：10 个一级类目、30 个品牌、约 200 个 SKU，价格区间按类目差异化设置（图书 19~299 元，手机数码 899~8999 元）；
- **区域分布**：20 个省份、按消费能力设置不同权重（广东 14%、江苏/浙江各 10%、北京/上海各 6%……）；
- **渠道分布**：APP 商城 34%、微信小程序 24%、天猫旗舰店 16%、PC 商城 14%、京东自营 12%；
- **支付方式**：支付宝 40%、微信支付 37%、银行卡 12%、花呗 7%、货到付款 4%；
- **订单状态**：已完成 62%、已支付 22%、待付款 7%、已取消 5%、已退款 4%；
- **时间分布**：91 天（2026-06-01 ~ 2026-08-30），周末销量系数 1.32，整体呈 0.4%/天的缓慢增长趋势，
  单日内的下单时刻按"午间 + 夜间"双高峰分布；
- **用户复购**：用户池 6 万人，产生约 10.7 万笔订单，人均约 1.8 单，存在真实复购行为。

> 生成器使用**固定随机种子**（`mock.seed=20260907`），因此每次生成的数据完全一致，作业结果可复现。

## 2. 数据字典

### 2.1 订单明细表 `ods_order_detail`

数据源：`data/raw/ods_order_detail.csv`

| 序号 | 字段名 | 中文名 | 数据类型 | 长度 | 允许为空 | 取值范围 / 枚举 | 业务含义与说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | order_id | 订单编号 | VARCHAR | 64 | 否 | `SO` + yyyyMMdd + 6 位流水，如 `SO20260601000001` | 一笔订单的唯一标识；一笔订单可包含 1~3 行商品明细，故本字段会重复出现 |
| 2 | order_time | 下单时间 | VARCHAR | 32 | **是** | `yyyy-MM-dd HH:mm:ss` / `yyyy/MM/dd HH:mm` / `yyyy-MM-dd'T'HH:mm:ss` | 订单创建时间；源数据存在多种格式，且含少量无法解析的脏值，需规整 |
| 3 | user_id | 用户编号 | VARCHAR | 32 | 否 | `U` + 6 位数字，如 `U018214` | 下单用户标识；已脱敏，不含任何真实个人信息 |
| 4 | product_id | 商品编号 | VARCHAR | 32 | 否 | `P` + 5 位数字，如 `P00111` | 关联商品维度表的商品标识 |
| 5 | channel | 销售渠道 | VARCHAR | 32 | 否 | APP商城 / 微信小程序 / 天猫旗舰店 / PC商城 / 京东自营 | 订单产生的销售渠道 |
| 6 | province | 收货省份 | VARCHAR | 32 | **是** | 广东省 / 江苏省 / 浙江省 / 北京市 / 上海市 等 20 个省级行政区 | 收货地址所在省份；存在空值，清洗时填充为"未知" |
| 7 | city | 收货城市 | VARCHAR | 64 | **是** | 广州市 / 深圳市 / 杭州市 等 | 收货地址所在城市；存在空值，清洗时填充为"未知" |
| 8 | quantity | 购买数量 | VARCHAR | 16 | **是** | 正常值 1~5 | 该行商品的购买件数；存在 0、负数、99999 等异常值，需校验 |
| 9 | unit_price | 商品单价 | VARCHAR | 16 | **是** | > 0，如 `395.84` | 该行商品的成交单价（元）；存在 0 或负值异常 |
| 10 | discount_amount | 优惠金额 | VARCHAR | 16 | **是** | ≥ 0，如 `84.51` | 该行商品享受的优惠金额（元） |
| 11 | pay_amount | 实付金额 | VARCHAR | 16 | **是** | ≥ 0，如 `311.33` | 该行商品实付金额（元）；理论上 = 数量 × 单价 − 优惠，源数据中存在不一致的情况 |
| 12 | order_status | 订单状态 | VARCHAR | 24 | **是** | 已完成 / 已支付 / 待付款 / 已取消 / 已退款 | 订单当前状态；存在非法枚举值（如"已妥投""PAID"），需标准化 |
| 13 | pay_type | 支付方式 | VARCHAR | 24 | **是** | 支付宝 / 微信支付 / 银行卡 / 花呗 / 货到付款 | 支付渠道；存在空值，清洗时填充为"未知" |

> 字段 8~11 在源数据中以**字符串**形式存储，这是企业数据落地的常见形态（源系统导出不加类型约束），
> 因此 ODS 层统一按字符串落库，类型规整在 DWD 层完成。

## 3. 脏数据注入说明

为支撑"数据清洗"环节的教学目标，生成器按固定比例注入了 8 类脏数据。注入比例与实测命中量如下：

| 规则编码 | 脏数据类型 | 注入比例 | 实测命中量 | 处理方式 |
| --- | --- | --- | --- | --- |
| R01 | 省份 / 城市 / 支付方式为空 | 约 1.0%~1.2% | 6,730 条 | 填充为"未知"，不丢弃 |
| R02 | 完全重复记录（13 个业务字段全部相同） | 约 1.2% | 2,381 条 | 去重，仅保留一条 |
| R03 | 下单时间无法解析（如 `2026/13/45 25:61:00`、`0000-00-00 00:00:00`、空值） | 约 1.5% | 2,975 条 | 丢弃并留痕 |
| R04 | 购买数量 ≤ 0 或 > 999 | 约 0.5% | 计入 R04-R06 合计 | 丢弃并留痕 |
| R05 | 商品单价 ≤ 0 | 约 0.4% | 计入 R04-R06 合计 | 丢弃并留痕 |
| R06 | 实付金额 ≠ 数量 × 单价 − 优惠（偏差 > 0.01 元） | 约 1.0% | 计入 R04-R06 合计 | 按公式重算修正，不丢弃 |
| R07 | 订单状态非合法枚举（如"已妥投""PAID""待确认""???"） | 约 0.4% | 814 条 | 标准化为"其他" |
| R08 | 商品主数据缺失 | 约 0.3% | 576 条 | 类目填充为"未知类目" |

> 说明：R04-R06 三项合计实测命中 3,781 条。规则之间可能存在重叠（同一行同时命中多条），
> 因此各规则命中数之和大于实际丢弃记录数（4,735 条）。

**清洗结果（实测）**

| 指标 | 数值 |
| --- | --- |
| 原始记录数 | 200,177 |
| 去重后记录数 | 197,796 |
| 丢弃记录数 | 4,735 |
| 有效记录数（进入 DWD） | 193,061 |
| 数据质量得分 | 96.45% |

## 4. 数据合规说明

1. **无真实个人信息**：全部数据由程序模拟生成，用户标识为 `U000001` 形式的脱敏编号，与任何真实自然人无关联；
2. **无敏感字段**：数据集中不包含手机号、身份证号、收货详细地址、支付账号等敏感信息，省市级以下地址粒度不涉及；
3. **成本价仅用于演示**：`cost_price` 字段为程序按比例生成的模拟值，不代表任何真实定价；
4. **可追溯**：所有被丢弃的异常记录均写入 `dwd_clean_reject` 表，保留批次号与原始记录片段，满足数据治理的可追溯要求；
5. **可重复**：随机种子固定，重复运行不会产生新的数据，符合数据一致性要求。
