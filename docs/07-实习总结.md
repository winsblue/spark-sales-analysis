# 七、实习总结

---

## 1. 实习概述

本次生产实习围绕"教学内容 · 大数据方向"开展，我选择了**实践项目 3：基于 Spark 的离线数据分析与 Java 服务化应用**，
以电商商品销售分析为业务场景，独立完成了从数据生成、数据清洗、多维指标计算、结果落库，
到 Java 后端服务化、Vue 前端可视化的完整链路，最终形成可运行、可演示、有完整文档的工程交付物。

项目按分层要求完成了**基础层（合格）**与**提高层（良好）**的全部内容：
基础层完成了数据读取、清洗、转换、聚合与结果输出，产出 9 项核心指标并通过 Java Web 页面展示；
提高层实现了多维分析、时间趋势、TopN、分组对比、结果持久化、分页查询与数据导出，
并用 RDD 与 DataFrame 两种方式实现了同一套指标以比较运行效果。

## 2. 技术收获

### 2.1 大数据处理

| 收获 | 具体体现 |
| --- | --- |
| 理解 Spark 的两种编程抽象 | RDD 面向对象、需要手工管理类型与序列化；DataFrame 面向结构化数据、由 Catalyst 优化。同一套指标用两种方式实现后，对二者的差异有了直观认识 |
| 掌握 DataFrame 的清洗技巧 | `coalesce` 多格式时间解析、`nullif + trim` 处理空串、窗口函数去重、`countDistinct(when(...))` 条件去重计数 |
| 理解广播关联的适用场景 | 商品维度仅 199 条，用 `broadcast` 后可走 Map 端关联，避免事实表参与 Shuffle |
| 掌握自定义累加器 | 用 `GroupStat` 同时累加 4 个去重集合与 3 个求和字段，让 `groupByKey` 与 `aggregate` 复用同一套逻辑 |
| 理解单机模式的边界 | `local[*]` 无需集群即可验证逻辑，但 shuffle 分区数、结果收集（`collect`）的内存占用仍需主动控制 |

### 2.2 数据仓库建模

项目采用 ODS / DWD / ADS 三层结构，让我真正理解了"分层不是为了好看，而是为了职责清晰"：

- **ODS 层全字段按字符串存储**，因为源系统导出不带类型约束；把类型规整推迟到 DWD 层，
  比在入库时就强制转换更容易定位数据问题；
- **DWD 层做一次清洗，下游全部复用**，避免了每个指标各写一套清洗逻辑导致口径不一致；
- **ADS 层的粒度设计决定了可扩展性**：最初我打算把 TopN 排名和占比直接固化到结果表，
  后来发现这样前端切换日期范围后排行榜不会变。最终改为"**按天存全量聚合，排名与占比在查询时计算**"，
  才真正做到筛选联动。

### 2.3 Java 后端开发

| 收获 | 具体体现 |
| --- | --- |
| Spring Boot 工程化 | 统一响应结构、全局异常处理、参数校验、跨域配置、接口文档 |
| MyBatis 动态 SQL | 用 `<if>` 标签拼装多条件查询，所有参数走 `#{}` 预编译占位符防止 SQL 注入 |
| 查询性能意识 | 明细表索引以 `stat_date` 为前导列，匹配"先按时间过滤、再按维度分组"的查询模式；分页使用物理分页而非内存分页 |
| 接口设计能力 | 14 个接口共用一套筛选参数，前端切换条件后所有图表同步刷新 |

### 2.4 前端可视化

- 掌握 ECharts 的折线、柱状、饼图与分组柱状图配置；
- 学会了**图表容器的封装**：把初始化、更新、`resize`、`dispose` 收敛到一个组件，业务视图只提供 `option`；
- 理解"**数据处理放在哪一层**"：交叉对比的扁平数据需要在前端转成"横轴 + 系列"结构，这类转换放在前端更合适。

## 3. 遇到的问题与解决过程

### 问题一：Spark 在 Windows 上无法启动

**现象**：首次运行作业时报 `Could not locate executable null\bin\winutils.exe in the Hadoop binaries`。

**排查**：Spark 底层依赖 Hadoop 的文件系统抽象，即使在 `local` 模式下也需要 `winutils.exe` 与 `hadoop.dll`
来提供 Windows 下的本地文件系统操作能力。

**解决**：下载 `hadoop-3.3.6` 对应的 `winutils.exe` 与 `hadoop.dll` 放到 `C:\hadoop\bin`，
配置 `hadoop.home.dir`，并在启动脚本中把该目录加入 `PATH`（`hadoop.dll` 需要能被 JVM 加载）。
同时把这个配置做成可覆盖项（配置项 → 环境变量 `HADOOP_HOME`），保证换到 Linux 环境无需改代码。

### 问题二：RDD 算子内部调用 Spark 动作导致任务失败

**现象**：RDD 方式的类目统计在本地小数据量下能跑通，跑全量时报
`org.apache.spark.SparkException: SparkContext can only be used on the driver`。

**原因**：最初为了拿到类目名称，我在 `map` 算子内部写了 `records.filter(...).take(1)`。
算子在 Executor 上执行，而 `SparkContext` 只存在于 Driver，属于典型的"在算子里调用动作"错误。

**解决**：把类目名称直接编入分组键（`stat_date|category_id|category_name`），
从根上避免算子内部的额外查询。这也让我理解了 Spark 的一条基本原则：
**算子内部只能做无副作用的计算，任何需要 Driver 参与的操作都必须先 `collect` 或 `broadcast` 出去。**

### 问题三：日志显示"写入 0 行"，但数据其实写进去了

**现象**：结果表批量写入后日志打印 `ads_overview 写入 0 行`，但查询数据库发现有 9 条数据。

**原因**：JDBC 连接串开启了 `rewriteBatchedStatements=true`（用于提升批量写入性能），
此时 MySQL 驱动对批量中的每条语句返回 `SUCCESS_NO_INFO`（-2）而不是实际影响行数，
而我最初的统计逻辑是"跳过负值后求和"，于是得到 0。

**解决**：改为统计"执行成功的语句数量"（`r >= 0 || r == SUCCESS_NO_INFO`）。
这件事让我意识到：**遇到"看起来不合逻辑"的现象，应该先去查数据本身，而不是怀疑业务逻辑。**

### 问题四：性能对比不公平

**现象**：第一次做两种计算方式的性能对比时，DataFrame 耗时 53.5 秒、RDD 耗时 43.0 秒，
结论是"RDD 更快"，但这与预期和常识不符。

**排查**：检查代码后发现，ODS 原始层装载（20 万行入库）被放在了 DataFrame 轮次里执行，
而 RDD 轮次没有做这一步 —— 也就是说 DataFrame 多干了一份活。

**解决**：把 ODS 装载提取为两种方式的**公共前置步骤**，只执行一次且不计入任何一方的耗时；
同时在作业日志的 `remark` 字段里注明各阶段耗时构成，避免以后再次误读。
修正后 DataFrame 33.5 秒、RDD 53.9 秒，符合"DataFrame 有 Catalyst 优化优势"的预期。

> **这是我本次实习体会最深的一点**：基准测试的结果如果与预期相反，第一反应应该是怀疑测试方法，
> 而不是急着下结论。一个不公平的对比会给技术选型带来完全错误的导向。

### 问题五：数据库版本兼容性

**现象**：目标环境是 MySQL 5.5.27，建表时使用 `utf8mb4` 报错，使用
`DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` 也报错。

**解决**：MySQL 5.5 不支持 `utf8mb4`，且只允许一个 `TIMESTAMP` 列带 `CURRENT_TIMESTAMP` 默认值。
最终统一改用 `utf8` 字符集、`DATETIME` 由程序显式赋值、驱动降级为 `mysql-connector-java 5.1.49`。
这让我体会到**"适配存量环境"也是工程能力的一部分**，不能假设所有环境都是最新版本。

## 4. 存在的不足

| 不足 | 说明 | 改进方向 |
| --- | --- | --- |
| 数据为模拟生成 | 分布参数是我按经验设定的，与真实电商数据仍有差距 | 接入公开数据集（如淘宝用户行为数据集）验证逻辑 |
| 单机模式限制 | `local[*]` 无法验证集群环境下的数据倾斜、资源调度问题 | 在伪分布式 Spark 集群上运行，观察 executor 与 shuffle 行为 |
| 缺少定时调度 | 目前需要手工执行作业 | 引入 Airflow 或 Quartz 做任务编排（属拓展层要求） |
| 无缓存与查询优化 | 每次请求都实打实查库 | 引入 Redis 缓存热点指标（属拓展层要求） |
| 无权限体系 | 任何人访问都能看到全部数据 | 增加登录与角色化看板（属拓展层要求） |
| 前端未做移动端适配 | 大屏看板在手机上的体验不佳 | 增加响应式布局与自适应大屏方案 |

## 5. 职业素养与团队协作体会

1. **规范编码**：项目统一了响应结构、异常处理、命名规范与注释风格。
   配置文件与代码分离，敏感信息（数据库口令）支持本地覆盖，避免误提交。
2. **数据合规意识**：数据全部模拟生成、用户标识脱敏、不含任何个人信息；
   被丢弃的异常数据全部留痕，满足可追溯要求。
3. **文档与交付**：文档不是"交差用的"，而是写给三个月后的自己看的。
   本次把 4 个踩坑记录写进文档，就是为了避免重复犯错。
4. **角色协作模拟**：虽然本项目由个人完成，但我按照"需求分析 → 数据建模 → 后端开发 → 前端开发 → 测试"
   的标准流程推进，每个阶段的产出物都对应到具体文档，体会到**接口约定先行**能大幅减少返工。
