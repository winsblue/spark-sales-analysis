## 第 4 页 · 技术选型

**要点**

| 层次 | 选型 | 版本 |
| --- | --- | --- |
| 数据计算 | Apache Spark（本地 / YARN 双模式） | 3.5.1 |
| 结果存储 | MySQL（ODS / DWD / ADS 三层） | 5.5.27 |
| 后端服务 | Spring Boot + MyBatis-Plus + OpenAPI | 2.7.18 / 3.5.3 |
| 前端可视化 | Vue 3 + Vite + ECharts | 3.4 / 5.5 |
| 构建 | Maven 多模块 | 3.8.8 |

**选型理由（重点讲 2 个）**

1. 选 Spark 而非 Hive/MapReduce：支持单机模式，无需部署集群即可验证逻辑；同时提供 RDD 与 DataFrame 两套 API，天然满足"比较不同处理方式"的要求；
2. 查询策略选"预计算 + 即席查询"混合：避免维度组合爆炸，同时保证筛选联动正确。

## 第 6 页 · 数据来源与数据字典

**要点**

- 数据为程序化模拟生成（20 万行订单明细、199 个商品、91 天、约 10.7 万笔订单）；
- 分布贴近真实：周末销量系数 1.32、日内双高峰、类目价格差异化、6 万用户池形成复购；

- **按比例注入 8 类脏数据**，作为清洗环节的输入；
- 数据合规：无真实个人信息、用户编号脱敏、异常记录全留痕。

> 提示：这一页解决评委最常问的"数据从哪来"。

## 第 7 页 · 数据清洗（核心亮点 1）

**要点**

| 类别 | 规则 | 策略 |
| --- | --- | --- |
| 可修复 | R01 空值、R06 金额不一致、R07 状态非法、R08 维度缺失 | 填充 / 重算 / 标准化，**保留记录** |
| 不可修复 | R03 时间无法解析、R04 数量非法、R05 单价非法 | **丢弃并留痕** |

**实测结果**

```
原始记录数 200,177  →  去重 2,381  →  丢弃 4,735  →  有效 193,061
数据质量得分 96.45%
```

**设计理念**：清洗的目标不是"丢掉脏数据"，而是**尽可能保住可用数据，只丢弃真正无法使用的记录**。

> 提示：强调"留痕表"是数据治理意识，被丢弃的数据可追溯到批次号与原始记录。

## 第 8 页 · 多维指标计算（核心亮点 2）

**要点**

- 9 项核心指标 + 7 张多维结果表（类目 / 商品 / 渠道 / 支付方式 / 省份 / 渠道×类目 / 每日趋势）；
- 关键实现：`countDistinct(when(条件, 字段))` —— 用条件去重计数在同一份数据上同时算出"下单量"与"有效订单量"；
- 指标口径统一：有效订单 = 已完成 / 已支付；GMV 只算有效订单，下单量含取消退款；
- 维度关联用 `broadcast` 广播小表，避免事实表参与 Shuffle。

---

## 第 9 页 · 两种计算方式对比（提高层要求）

**要点**

| 对比项 | DataFrame / SparkSQL | RDD |
| --- | --- | --- |
| 数据读取 | `spark.read().schema().csv()` | `textFile()` + 手工 `split` |
| 类型处理 | 内置 `cast`，非法自动为 null | 逐个字段手工解析校验 |
| 去重 | 窗口函数 `row_number()` | `distinct()` |
| 分组聚合 | `groupBy().agg()` | `mapToPair().groupByKey()` + 自定义累加器 |
| 维度关联 | `broadcast` Join | `Broadcast` 变量 + Map 手动关联 |
| 代码量 | 约 300 行 | 约 620 行 |
| **实测总耗时** | **36.6 秒** | **51.7 秒** |
| 其中清洗阶段 | 12.2 秒 | **4.3 秒**（RDD 更快） |
| 其中聚合与落库 | **24.4 秒** | 47.5 秒 |

**结论**：DataFrame 整体快 **41.3%**，代码量少一半，可读性显著更好 →
**离线分析场景应优先使用 DataFrame / SparkSQL**，RDD 更适合需要精细控制底层行为的场景。
有意思的是 RDD 在清洗阶段反而更快（一次 map 转换，没有 DataFrame 多次 `withColumn` 与窗口函数的开销），
但聚合阶段 Catalyst 优化与 Tungsten 编码的收益远大于这点损失。

> 提示：这里是加分点，评委很在意"你有没有真的比较过"。可以补一句：
> "一开始的对比结果与预期相反，排查后发现是 ODS 装载只算在了 DataFrame 那一轮，修正后才得到公平数据。"

## 第 10 页 · 数据仓库分层与查询策略（核心亮点 3）

**要点**

- 分层：ODS（原始，全字符串）→ DWD（清洗，类型规范）→ ADS（预计算指标）；
- **ADS 表按"统计日期 + 维度"存全量聚合，排名与占比由后端查询时计算**；
  - 若把 TopN 固化进结果表，前端切换日期范围后排行榜不会变 → 无法实现真正的筛选联动；
- 查询策略：

| 筛选情况 | 查询路径 | 原因 |
| --- | --- | --- |
| 仅日期范围（默认） | 读取 ADS 预计算表 | 响应快 |
| 含渠道/类目/省份 | 对 DWD 即席聚合 | 保证任意组合联动正确 |

- 两条路径由"**数据一致性校验**"接口交叉验证（`/api/monitor/consistency`）。

## 第 11 页 · Java 后端服务化

**要点**

- Spring Boot 2.7 + MyBatis-Plus，14 个 RESTful 接口；
- 工程化实践：统一响应结构 `{code,message,data}`、全局异常处理、参数校验、CORS、OpenAPI 接口文档；
- 多维查询用 MyBatis 动态 SQL（`<if>` 标签），所有参数走 `#{}` 预编译占位符防注入；
- 明细下钻使用物理分页；导出 CSV 带 UTF-8 BOM，Excel 打开不乱码；
- **性能优化（重点）**：三个真实定位过的慢查询问题
  1. MySQL 5.5 默认 `tmp_table_size` 仅 18MB，`COUNT(DISTINCT)` 去重集合溢写磁盘 → 连接级调大后趋势查询 **37.4s → 2.1s**；
  2. 明细表上未被使用的 `idx_dwd_product` 让优化器误选二级索引，造成 19 万次回表 → 移除后商品排行 **40.9s → 2.1s**；
  3. 商品排行扫描量过大 → 默认视图改走预计算表，**26.7s → 173ms（154 倍）**。

> 提示：这三个优化故事很能体现"会看现象、会定位根因、懂得权衡"，建议重点讲，
> 并在被问到时说明：**索引不是越多越好，未被查询使用的索引既拖慢写入又会误导优化器。**

## 附：答辩可能被问到的问题及回答要点

| 可能的问题 | 回答要点 |
| --- | --- |
| 为什么不用 Hive？ | Hive 适合大批量离线分析，但查询延迟高，不适合后端接口直接查询；本项目结果落 MySQL 更适合服务化。（本项目也保留了 ODS/DWD/ADS 的分层思想） |
| 为什么不做实时？ | 属于拓展层要求，按要求不做。若要做，链路上加 Kafka + Flink，ADS 层结果替换为实时写入即可，后端接口不用改。 |
| 数据量这么小，为什么要用 Spark？ | 本项目定位是打通技术链路；Spark 的收益随数据量增长而放大。当前已用 20 万行验证逻辑正确性，并预留了集群提交能力（`--master yarn`）。 |
| 预计算和即席查询会不会口径不一致？ | 会，所以做了 `/api/monitor/consistency` 接口自动比对，4 项可加指标差值均为 0；不可加指标（如用户数）不参与逐项比对，已在文档说明原因。 |
| RDD 比 DataFrame 慢，是不是 RDD 实现有问题？ | RDD 实现里做了更多手工校验，且没有 Catalyst 优化与 Tungsten 编码；这也是结论本身想说明的问题——离线分析优先用 DataFrame。 |
| 如果数据量涨到 1 亿行会怎样？ | 单机模式顶不住，需切到 YARN 集群；同时要处理数据倾斜（按类目/日期加盐）、调整分区数、把 ADS 汇总粒度改为预聚合宽表。 |
| 数据一致性怎么保证的？ | 三点：① 指标口径集中定义在 `Schemas` 与文档中；② 两者实现共用同一份 DWD 明细；③ 提供自动比对接口。 |
| 项目最大的难点是什么？ | 不是写 Spark 代码，而是"把口径想清楚"。例如最初把 TopN 固化进结果表，导致筛选不联动，返工重做了 ADS 层设计。 |
