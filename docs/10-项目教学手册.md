### 1.5 术语速查（看代码遇到不认识的就回这里）

| 术语 | 一句话解释 |
| --- | --- |
| **ODS** | Operational Data Store，原始层。数据原样进来，不做类型转换，方便追溯 |
| **DWD** | Data Warehouse Detail，明细层。清洗、类型规范后的干净明细 |
| **ADS** | Application Data Store，应用层。按分析维度预聚合好的结果表 |
| **ETL** | Extract-Transform-Load，抽取-转换-加载。本项目是"读 CSV → 清洗统计 → 写 MySQL" |
| **幂等** | 同一个操作执行多次，结果和执行一次相同。本项目靠"先 TRUNCATE 再写"实现 |
| **宽表** | 把多个维度的字段冗余在一张表里，用存储换查询速度 |
| **广播 Join** | 把小表复制到每个计算节点，避免大表参与 Shuffle |
| **Shuffle** | 跨节点重新分发数据（如 groupBy 需要按 key 汇聚），是 Spark 最贵的操作 |
| **可加指标** | 可以跨维度直接求和的指标（GMV、件数）；用户数是**不可加**的（会重复计数） |
| **即席查询** | 不预先算好，收到请求时才去查明细聚合（准但慢） |
| **预计算** | 作业运行时就把结果算好存起来，请求时直接读（快但维度固定） |

## 2. 技术选型：为什么是这些技术

面试最爱问"你为什么用 X"。**回答的套路是：先说候选，再说约束，最后说理由和代价。**

### 2.1 为什么用 Spark，而不是 Hive / MapReduce

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| MapReduce | 稳定、教程多 | 代码量大、中间结果落盘、迭代慢 | ❌ 开发效率太低 |
| Hive | SQL 友好、适合大批量 | 查询延迟高（分钟级），不适合后端接口直查 | ❌ 本项目要服务化，延迟敏感 |
| **Spark** | 内存计算、提供 RDD 与 DataFrame 两套 API、有 `local` 模式 | 内存占用高 | ✅ **选它** |

**选 Spark 的决定性理由（划重点）**：
1. 它同时提供 RDD 和 DataFrame/SparkSQL —— 正好满足提高层"比较不同处理方式运行效果"的要求；
2. 支持 `local[*]` 单机模式 —— 不用搭集群就能验证逻辑，开发成本低；
3. 支持 `--master yarn` —— 又能上集群，一份代码两种环境。

### 2.2 为什么结果存 MySQL，而不是 HDFS / Hive

后端接口要毫秒~秒级响应，MySQL 有索引、支持复杂 WHERE 与排序，比 HDFS 适合"点查 + 聚合"。
HDFS 适合存海量原始数据与中间结果，不适合直接服务 Web 请求。

**我们其实两样都用了**：源数据放 HDFS，结果指标放 MySQL —— 这才是数仓的标准分层思路。

### 2.3 环境约束怎么影响选型（体现你会看现实条件）

| 约束 | 后果 | 怎么处理 |
| --- | --- | --- |
| JDK 只有 8 | **Spring Boot 3.x 需要 JDK 17** | 只能用 Spring Boot 2.7.x |
| MySQL 5.5.27 | 不支持 `utf8mb4`、不支持 `DATETIME DEFAULT CURRENT_TIMESTAMP`、驱动必须用 5.1.x | 字符集用 `utf8`，时间字段由程序赋值，驱动锁定 `mysql-connector-java 5.1.49` |
| Windows 跑 Spark | 缺 `winutils.exe` / `hadoop.dll` | 下载放到 `C:\hadoop\bin` 并配置 `hadoop.home.dir` |
| Hadoop 3.1.3（2018 年） | Spark 3.5.x 自带 hadoop-client 3.3.4，新客户端连旧服务端上 YARN 有协议风险 | 用 `--master local[*]` 跑，数据源走 HDFS —— 用到 HDFS，但绕开 YARN 兼容问题 |

> **这话术很重要**："我没有一味追求新版本，而是先摸清环境约束再定方案" —— 这是工程思维。

## 3. 数据建模与数据生成

### 3.1 💡 原理：为什么要分三层

**不分层会怎样**：每个指标各写一套清洗逻辑 → 同一份数据算出不同结果 → 口径不一致 → 报表不可信。

分层解决的是**职责单一**：

| 层 | 存什么 | 特点 | 类比 |
| --- | --- | --- | --- |
| ODS | 原始数据 | 全字段字符串、不做任何处理 | 仓库收货区 |
| DWD | 清洗后明细 | 类型规范、规则统一、脏数据被剔除或留痕 | 加工车间 |
| ADS | 聚合结果 | 按分析场景预聚合，直接可查 | 门店货架 |

**好处**：清洗逻辑只写一次、下游全部复用；出问题能逐层回溯。

### 3.2 表结构设计（14 张表）

| 层 | 表 | 说明 |
| --- | --- | --- |
| ODS | `ods_order_detail` / `ods_product` | 原始层，全字段 `VARCHAR` |
| DWD | `dwd_order_detail` | 清洗后明细（19.3 万行） |
| DWD | `dwd_clean_reject` | **被丢弃记录留痕**（含违反的规则编码） |
| ADS | `ads_overview` | 9 项核心指标 |
| ADS | `ads_daily_trend` | 每日趋势（91 行） |
| ADS | `ads_category_stat` | 类目 × 日 |
| ADS | `ads_product_stat` | 商品 × 日 |
| ADS | `ads_channel_stat` | 渠道 × 日 |
| ADS | `ads_paytype_stat` | 支付方式 × 日 |
| ADS | `ads_region_stat` | 省份 × 日 |
| ADS | `ads_channel_category_stat` | 渠道 × 类目 × 日（**交叉分析**） |
| 监控 | `ads_clean_stat` | 数据质量报告 |
| 监控 | `etl_job_log` | 作业日志（含两种计算方式耗时） |

**设计要点**：所有 ADS 表都是「**统计日期 + 维度**」粒度，存的是**全量聚合值**而不是 TopN 排名。
原因见 5.2 —— 这是这个项目最重要的一个设计决策。

### 3.3 数据生成：怎么让"假数据"像真的

纯随机会造出"每天销量一样、每个人买一样多"的假数据，算出来的指标毫无业务含义。
所以生成器里塞了这些**业务规律**：

| 规律 | 实现 | 效果 |
| --- | --- | --- |
| 周末销量高 | 周末系数 1.32 | 趋势图有明显波峰（实测周末 ~1,370 单 vs 工作日 ~1,020 单） |
| 日内双高峰 | 中午 12 点、晚上 20 点权重高 | 分时分布合理 |
| 类目价格分层 | 手机数码均价高、食品生鲜低 | 类目 GMV 排名有差异 |
| 用户复购 | 6 万用户池（107 笔订单 /46,316 人 ≈ 2.3 单/人） | 用户数与订单量不是 1:1，符合真实电商 |
| 渠道流量差异 | 各渠道权重不同 | 渠道占比有梯度 |
| 结果可复现 | 固定随机种子 `20260907` | 每次生成的数据**逐位一致**，便于对比实验 |

### 3.4 ⭐ 8 类脏数据：这是本项目的"题库"

**为什么要主动造脏数据？** 因为真实数据一定有脏数据，而"清洗能力"是这个项目的核心加分项。
造出来的每一类都对应一条清洗规则：

| 规则 | 脏数据类型 | 处理策略 | 实测命中 |
| --- | --- | --- | --- |
| R01 | 省份/城市/支付方式为空 | **填充**"未知"，保留记录 | 6,730 |
| R02 | 13 个字段完全相同的重复行 | **去重**，只留第一条 | 2,381 |
| R03 | `2026/13/45 25:61:00`、`invalid_time`、空值 | **丢弃**（没法用） | 2,975 |
| R04 | 数量 = 0 / -1 / 99999 | **丢弃** | ↓ 合并 |
| R05 | 单价 = 0 或负数 | **丢弃** | ↓ 合并 |
| R06 | 实付金额 ≠ 数量×单价−优惠 | **按公式重算**，保留 | 3,781 |
| R07 | 状态 = "已妥投" / "PAID" / "???" | **标准化**为"其他" | 814 |
| R08 | 引用了不存在的商品编号 | **填充**"未知类目"，保留事实 | 576 |

**⭐ 关键设计理念（这句话要背下来）**：

> 清洗的目标**不是"把脏数据都删掉"，而是"尽可能保住可用数据，只丢弃真正无法使用的记录"**。
> 能修复的就修复（R01/R06/R07/R08），修复不了的才丢弃（R03/R04/R05），
> 而且丢弃的每一条都进留痕表，可追溯到批次号和原始内容。

**实测结果**：

```
原始记录数 200,177
  ├─ R02 重复          2,381  → 去掉
  ├─ R03/R04/R05 丢弃  4,735  → 进留痕表
  └─ 有效进入 DWD     193,061
数据质量得分 = 193,061 ÷ 200,177 = 96.45%
```

**平衡校验（答辩时常被问"数据对得上吗"）**：

```
raw = dup + discard + valid
200,177 = 2,381 + 4,735 + 193,061   ✅ 恒等成立
```

1. **为什么 ODS 层全字段都用字符串？**
   因为源数据没有类型约束、可能包含脏值。先把类型问题隔离在 ODS，让原始数据保持原貌可追溯；

## 4. Spark 数据处理核心

### 4.1 💡 原理：RDD、DataFrame、SparkSQL 是什么关系

```
        SparkSQL  ← SQL 语句 / Dataset API（结构化、类型安全）
            ↑
        DataFrame ← 带 schema 的分布式表（类似 Pandas DataFrame，但是分布式的）
            ↑
          RDD     ← 最底层的分布式对象集合（你可以完全控制每个元素怎么算）
```

| 维度 | RDD | DataFrame / SparkSQL |
| --- | --- | --- |
| 数据形态 | 一堆 Java/Scala 对象 | 有列名和类型的二维表 |
| 优化 | 无（你写什么就执行什么） | **Catalyst 优化器**会重排、下推、剪枝 |
| 存储 | JVM 对象（有序列化开销） | **Tungsten** 堆外二进制编码 |
| 代码量 | 多（手工解析、手工聚合） | 少（声明式） |
| 适合 | 非结构化数据、需要精细控制 | 结构化数据、聚合分析 |

**Spark 执行时会发生什么（理解这个才懂"为什么慢"）**：

```
你写的代码 → 逻辑计划 → Catalyst 优化 → 物理计划 → DAG → Stage → Task
                                                            ↑
                                        Stage 的边界就是 Shuffle（宽依赖）
```

- **窄依赖**：一个父分区的数据只给一个子分区（如 `map`、`filter`）→ 不需要跨节点搬运
- **宽依赖**：多个父分区的数据要重分发（如 `groupBy`、`join`）→ **触发 Shuffle，最贵**

> **本项目里的 Shuffle 点**：`groupBy(...).agg(...)` 每一次都会 Shuffle。所以 7 个维度就是 7 次 Shuffle。

### 4.2 🔧 本项目的清洗实现（DataFrame 版核心技巧）

#### 技巧 1：多格式时间解析 —— `coalesce` 逐级兜底

```java
Column ts = coalesce(
        to_timestamp(col("order_time"), "yyyy-MM-dd HH:mm:ss"),
        to_timestamp(col("order_time"), "yyyy/MM/dd HH:mm"),
        to_timestamp(col("order_time"), "yyyy-MM-dd'T'HH:mm:ss"));
Column badTime = ts.isNull();   // 三种格式都解析失败 → 判定为 R03 脏数据
```

`coalesce` 返回第一个非 null 的值。逐级尝试多种格式，全部失败就说明这条记录的时间没法用。

#### 技巧 2：窗口函数去重（R02）

```java
Dataset<Row> rawWithId = rawOrders.withColumn("rid", monotonically_increasing_id());
WindowSpec w = Window.partitionBy(   // 13 个业务字段作为去重键
        Schemas.ORDER_RAW_FIELDS).orderBy(col("rid"));
Dataset<Row> deduped = rawWithId
        .withColumn("rn", row_number().over(w))   // 同组内编号
        .filter(col("rn").equalTo(1))             // 只留第一条
        .drop("rn", "rid")
        .persist();                               // 缓存，后面要多次用
```

**为什么加 `rid` 再排序？** 保证去重结果稳定（每次跑留下的是同一条），否则结果不可复现。
**`.persist()` 为什么重要？** 这份数据后面要被反复使用，缓存到内存避免重复计算。

> ⚠️ RDD 方式的去重只需要 `distinct()` —— 一个例子说明 DataFrame 不一定更简洁，
> 但在聚合场景 DataFrame 更省事。

#### 技巧 3：条件聚合（本项目的招牌技巧）

同一个订单既要算进"下单量"（含取消/退款），又要算进"有效订单量"（排除），
**不需要跑两遍数据**：

```java
Column isValid       = col("is_valid_order").equalTo(lit(1));
Column validOrderId  = when(isValid, col("order_id"));                    // 无效订单 → null
Column validPay      = when(isValid, col("pay_amount")).otherwise(lit(BigDecimal.ZERO));
Column validUserId   = when(isValid, col("user_id"));
Column refundOrderId = when(col("order_status").equalTo(lit("已退款")), col("order_id"));

dwd.groupBy("stat_date").agg(
        countDistinct(col("order_id")).as("order_cnt"),       // 全部订单
        countDistinct(validOrderId).as("valid_order_cnt"),    // 只算有效订单
        sum(validPay).as("gmv_raw"),                          // 无效订单金额按 0 计
        sum(validQty).as("sales_qty"),
        countDistinct(validUserId).as("buyer_cnt"),
        countDistinct(refundOrderId).as("refund_order_cnt"))
```

**关键点**：`countDistinct` 会**自动忽略 null**，所以 `when(isValid, order_id)` 天然实现了"只统计有效订单"。
`sum` 用 `otherwise(0)` 而不是 null —— null 参与 sum 虽然也没事，但显式写 0 意图更清楚。

> **这个技巧一定要会讲**：它把"多口径统计"从"跑多遍数据"变成"一次分组多个聚合"，
> 既省 IO 又保证各口径看到的是**同一份数据**（不会出现口径间不一致）。

#### 技巧 4：广播关联（R08 维度补充）

商品维度只有 199 行，订单明细 20 万行。如果用普通 `join`，两张表都要参与 Shuffle：

```java
// 思路示意：小表广播到每个 Executor，大表就在本地完成关联，避免 Shuffle
Dataset<Row> joined = orders.join(broadcast(products), "product_id", "left_outer");
```

**判断标准**：小表默认阈值 10MB（`spark.sql.autoBroadcastJoinThreshold`）以内就广播。
本项目 199 行商品表 ~15KB，广播后**大表完全不参与 Shuffle**。

### 4.3 🔧 7 个维度统计 + 总览指标

```java
// 类目维度：按 日期 + 类目 分组
r.category = dwd.groupBy("stat_date", "category_id", "category_name").agg(
        sum(validPay).as("gmv_raw"),
        sum(validQty).as("sales_qty"),
        countDistinct(validOrderId).as("order_cnt"),
        countDistinct(validUserId).as("buyer_cnt"))
    .withColumn("gmv", col("gmv_raw").cast(DataTypes.createDecimalType(20, 2)))
    .withColumn("update_time", current_timestamp())
    .select(Cols.of(Schemas.CATEGORY_COLUMNS));
```

**三个细节值得注意**：

1. **金额用 `Decimal(20,2)` 而不是 double** —— 金额计算绝不能用浮点数（0.1+0.2≠0.3）；
2. **分组键带 `category_name`** —— 冗余名称是为了让后端不用再 join 一次维度表；
3. **`Cols.of(...)`** —— 统一列选择，列顺序集中在 `Schemas` 定义，避免"插入顺序对不上"这种低级错误。

### 4.4 🔧 指标口径：本项目最容易出错、也最能体现业务理解的地方

这是**全项目最重要的业务知识点**，答辩必考。

#### 口径定义表

| 指标 | 定义 | 可加性 |
| --- | --- | --- |
| 有效订单 | `order_status` ∈ {已完成, 已支付} | — |
| GMV（成交金额） | **有效订单**的实付金额之和 | ✅ 可加 |
| 下单量 | 去重后的订单编号数量（**含**取消/退款） | ✅ 可加 |
| 有效订单量 | 有效订单的订单编号数量 | ✅ 可加 |
| 销售件数 | 有效订单的商品数量之和 | ✅ 可加 |
| 下单用户数 | 产生有效订单的**去重**用户数 | ❌ **不可加** |
| 客单价 | GMV ÷ 有效订单量 | ❌ 不可加 |
| 件单价 | GMV ÷ 销售件数 | ❌ 不可加 |
| 退款率 | 退款订单量 ÷ 下单量 | ❌ 不可加 |
| 折扣率 | 优惠金额 ÷ 原价金额（数量×单价） | ❌ 不可加 |

#### ⭐ 什么叫"不可加"，为什么这么重要

**举例**：周一有 100 个用户下单，周二有 120 个用户下单，
如果直接把两天相加得到 220 —— **这是错的**，因为可能有人两天都买了（重复计数）。

所以：
- **可加指标**可以跨天/跨维度直接相加（GMV 可以：周一周二 GMV 相加就是两天总和）
- **不可加指标**必须**回到明细重新去重计算**（用户数必须去重后 count，不能把每天的相加）

**这个认知直接影响了本项目的两处设计**：

1. **一致性校验接口只比对可加指标**。如果把"用户数"也拿去比对（预计算表里每天的用户数相加 vs 明细去重），
   必定对不上 —— 那不是数据错，是指标性质决定的。
2. **趋势图里的用户数是"每日口径"**，没有"累计用户数"这个概念（累计必须重新去重）。

### 4.5 🔧 RDD vs DataFrame 双实现（提高层要求的核心）

同一个业务逻辑写两遍，才能公平对比。

| 环节 | DataFrame / SparkSQL | RDD |
| --- | --- | --- |
| 读取 | `spark.read().schema().csv()` | `textFile()` + 手工 `split(",")` |
| 类型处理 | 内置 `cast`，非法自动 null | 逐个字段手工 `try/catch` 解析 |
| 去重 | 窗口函数 `row_number()` | `distinct()` |
| 分组聚合 | `groupBy().agg()` | `mapToPair().groupByKey()` + 自定义累加器 |
| 维度关联 | `broadcast` Join | `Broadcast` 变量 + Map 手动匹配 |
| 代码量 | 约 300 行 | 约 620 行（**多一倍**） |

**RDD 侧的自定义累加器（GroupStat）**：要同时累加 4 个去重集合 + 3 个求和字段，
所以把 `groupByKey` 和 `aggregate` 两条路径的逻辑收敛到一个累加器类里，避免写两套。

**⭐ 实测结果（真实数据，不是估的）**：

| 阶段 | DataFrame | RDD | 谁快 |
| --- | --- | --- | --- |
| 清洗 | 12,216 ms | **4,266 ms** | RDD 快 2.9 倍 |
| 统计与落库 | **24,412 ms** | 47,481 ms | DataFrame 快 1.9 倍 |
| **总耗时** | **36,628 ms** | **51,747 ms** | **DataFrame 快 41.3%** |

**结论**：DataFrame 整体快 41.3%、代码量少一半，**离线结构化分析应优先用 DataFrame**；
RDD 在简单转换（清洗）上反而更快，因为它没有 Catalyst 优化与编码转换的固定开销，
但一到分组聚合就被 Tungsten 编码反超。

> **⭐ 这里有个必须会讲的故事（体现工程严谨性）**：
> 第一次做对比时得到的是"**RDD 比 DataFrame 快**"的相反结论。
> 排查后发现 **ODS 装载（20 万行入库）只算进了 DataFrame 那一轮**，RDD 轮次没做这步 —— 两者工作量不等价。
> 修正为"ODS 装载作为公共前置步骤、不计入任何一方耗时"后，才得到上面的公平数据。
>
> **结论升华**：基准测试结果与预期相反时，**先怀疑测试方法，再怀疑结论**。

### 4.7 ❓ 自查

<details>
<summary>点击看答案</summary>

1. **`countDistinct(when(条件, 字段))` 为什么能实现"条件去重计数"？**
   `when` 在条件不成立时返回 null，而 `countDistinct` 会忽略 null，
   所以只有满足条件的记录才会被计入去重计数。
2. **为什么金额要用 Decimal 而不是 double？**
   double 是二进制浮点数，无法精确表示 0.1 这类十进制小数，累加 20 万次会产生可见误差。
   Decimal 是定点数，金额计算必须用它。
3. **本项目有几次 Shuffle，分别在哪？**
   主要 8 处：7 个维度各一次 `groupBy`，加上总览指标的全局 `agg`；
   另外去重用的窗口函数也涉及 Shuffle（`partitionBy` 决定）。清洗阶段的 `filter`/`withColumn` 是窄依赖，不 Shuffle。
4. **用户数为什么不能跨天相加？**
   同一个用户可能多天都下单，相加会把同一个人重复计数，导致"总用户数"虚高。
   正确做法是回到明细层对用户去重后计数。

## 5. 结果落库与查询策略（本项目最有含金量的设计）

### 5.1 🔧 JDBC 批量写入的两个真实坑

**坑 1：`executeBatch()` 返回 -2，导致日志显示"写入 0 行"**

```java
// ❌ 错误写法：把返回值相加
long n = 0;
for (int r : results) { if (r >= 0) n += r; }
// 开启 rewriteBatchedStatements 后，驱动对批量中每条语句返回
// Statement.SUCCESS_NO_INFO (-2)，被 if 过滤掉 → n 永远是 0

// ✅ 正确写法：统计"执行成功的语句数量"
long n = 0;
for (int r : results) { if (r >= 0 || r == Statement.SUCCESS_NO_INFO) n++; }
```

> 现象是"日志说写入 0 行，但数据库里明明有数据"。**教训：遇到不合逻辑的现象，先去查数据本身。**

**坑 2：为什么要 `rewriteBatchedStatements=true`**
MySQL 驱动默认把批量 INSERT 一条条发给服务端，网络往返极多。开启这个参数后驱动会重写成
`INSERT ... VALUES (...),(...),(...)` 一条大语句，写入速度可提升数倍。代价就是返回值变成 -2。

### 5.2 ⭐ 查询策略：预计算 + 即席聚合的"双路径"

#### 问题：怎么让筛选条件真正生效

最初的做法很自然：作业里直接把 TopN 排名算好存进结果表。
**结果踩坑了** —— 前端把日期范围从"全周期"改成"最近 7 天"，排行榜**纹丝不动**。
因为排名是"全周期"算好的快照，后端只是把它读出来而已。

**修正后的设计**：

> ADS 表按「**统计日期 + 维度**」存**全量聚合值**（GMV、件数、订单量），
> **排名和占比一律由后端在查询时现算**。

这样前端无论怎么筛（日期、渠道、类目、省份），后端都能基于**筛选范围内**的数据重新排名和算占比，
图表才能真正联动。

#### 双路径策略

| 筛选情况 | 查询路径 | 为什么 | 实测耗时 |
| --- | --- | --- | --- |
| 只有日期范围（默认视图） | 读 **ADS 预计算表** | 数据量小、响应快 | 4~350 ms |
| 含渠道/类目/省份等维度 | 对 **DWD 明细即席聚合** | 预计算表没有这些维度，必须回明细 | 0.2~2 s |

代码分支长这样：

```java
public List<MetricItemVO> categoryRank(AnalysisQuery query) {
    prepare(query);            // 参数规整（日期校验、交换颠倒范围、限制 limit 上限）
    List<MetricItemVO> list = hasDimensionFilter(query)
            ? analysisMapper.selectCategoryStat(query)      // 即席聚合（DWD）
            : analysisMapper.selectCategoryStatFromAds(query); // 预计算（ADS）
    // 排名与占比统一在这里计算 —— 不固化进结果表，才能随筛选变化
    fillRankAndRatio(list);
    return list;
}
```

**同样的思路用在商品排行的性能优化上**（见 6.4）：默认视图走 `ads_product_stat`，
扫描量从 19 万行降到 1.8 万行。

### 5.3 ⭐ 幂等设计

**问题**：作业跑第二遍时，结果表里会不会出现两份数据？

**方案**：所有结果表**先清空再写入**（`TRUNCATE` 后再批量 INSERT），
每次运行生成唯一 `batch_id`（如 `B20260921142547-DF`）写进结果表便于追溯。

**收益**：
- 作业可以随便重跑，结果不会重复累积；
- 出问题能凭 `batch_id` 定位是哪一次跑的；
- 数据可复现（固定随机种子 + 幂等写入）。

## 6. Java 后端（Spring Boot）

### 6.1 💡 原理：为什么要有 DTO / VO / Entity 三套对象

| 后缀 | 全称 | 用途 | 例子 |
| --- | --- | --- | --- |
| **DTO** | Data Transfer Object | 接收前端传来的**请求参数** | `AnalysisQuery`（日期、渠道、limit） |
| **Entity** | — | 映射**数据库表** | `AdsOverview`、`DwdOrderDetail` |
| **VO** | View Object | 返回给前端的**视图对象** | `KpiCardVO`、`MetricItemVO` |

**不分会怎样**：前端传的参数字段和数据库字段同名混用，一旦表结构变了接口就崩，
或者暴露了不该给的字段（比如把 `batch_id` 返回给前端）。
分开之后，**数据库怎么改都不会污染接口契约**。

### 6.2 🔧 工程化四件套

```java
// ① 统一响应结构：前端只需判断 code
public class Result<T> {
    private int code;        // 0 = 成功
    private String message;  // "success" 或错误描述
    private T data;
    private long timestamp;
}

// ② 全局异常处理：业务异常 → 友好提示，未知异常 → 500 但不暴露堆栈
@RestControllerAdvice
public class GlobalExceptionHandler { ... }

// ③ 参数校验：非法日期、超限分页在入口拦住
private void prepare(AnalysisQuery q) {
    if (q.getStartDate() != null && q.getEndDate() != null
            && q.getStartDate().compareTo(q.getEndDate()) > 0) {
        String t = q.getStartDate(); q.setStartDate(q.getEndDate()); q.setEndDate(t);  // 自动交换
    }
    q.setLimit(Math.min(q.getLimitOrDefault(), MAX_LIMIT));   // 上限 100
}
```

**④ 防 SQL 注入**：所有参数走 MyBatis 的 `#{}` 预编译占位符，**绝不用 `${}` 拼接**：

```xml
<if test="q.channel != null and q.channel != ''">
    AND channel = #{q.channel}      <!-- ✅ 预编译，安全 -->
</if>
```

> `${}` 是字符串拼接，等于把用户输入直接塞进 SQL，会被注入。**面试常问，记住这句话。**

### 6.3 🔧 CSV 导出为什么要加 BOM

```java
// UTF-8 编码的文件，Excel 默认按 GBK 解析 → 中文乱码
// 开头写入 BOM（字节序标记 EF BB BF）后，Excel 就能正确识别为 UTF-8
out.write(0xEF); out.write(0xBB); out.write(0xBF);
```

**这是个很实用的细节**：不加 BOM，导出的 CSV 用 Excel 打开全是乱码；加了就正常。
这类"用户能直接感知"的细节，答辩演示时很容易加分。

### 6.4 ⭐ 三个真实性能优化案例（这是最能体现能力的一段）

#### 案例 1：`tmp_table_size` 太小导致临时表溢写磁盘

**现象**：趋势查询 37 秒超时。

**定位过程**：
```
① EXPLAIN 显示 Using temporary; Using filesort
② SHOW VARIABLES LIKE 'tmp_table_size'  →  18,874,368（仅 18MB）
③ 分析：COUNT(DISTINCT order_id) 需要在临时表里维护去重集合，
        19 万行的去重集合超过 18MB → 被迫落盘 → 慢十几倍
```

**解决**：连接池建立连接时把会话级临时表上限调大：

```yaml
spring:
  datasource:
    hikari:
      connection-init-sql: SET SESSION tmp_table_size=134217728, SESSION max_heap_table_size=134217728
```

**效果**：37,370 ms → **2,114 ms**（17.7 倍）
**为什么不改 my.ini？** 改全局配置要重启数据库、影响别人；连接级设置只影响本应用，更安全。

#### 案例 2：索引把优化器带偏，造成 19 万次回表

**现象**：商品排行 40 秒。

**定位**：
```
EXPLAIN 输出：key = idx_dwd_product   rows = 192,928   Extra = Using temporary; Using filesort
```

明细表上有 `idx_dwd_product (product_id)`，但这个项目的查询模式是"**按日期范围 + 维度分组聚合**"，
**从来不按商品筛选明细**。优化器误选了这个二级索引 → 每行都要回表取完整数据 → 19 万次随机 IO。

**解决**：从 DWD 表移除 `idx_dwd_product` 和 `idx_dwd_user`。

**效果**：40,930 ms → **2,110 ms**（19.4 倍）

> **⭐ 这是"索引不是越多越好"的活教材**：没被查询用到的索引，既拖慢写入，又会误导优化器。
> 建索引前先问"哪个查询会用它"。

#### 案例 3：扫描量过大 —— 换数据源

商品排行的分组键包含三个长字符串列（商品名/类目名/品牌），临时表索引长度超 1KB，即使调大上限仍可能落盘。

**解决**：默认视图（无维度筛选）下改从预计算表 `ads_product_stat` 读，扫描量 **19 万行 → 1.8 万行**。

**效果**：26,650 ms → **173 ms**（154 倍）

#### 优化小结（可以直接写进简历）

| 优化项 | 手段 | 效果 |
| --- | --- | --- |
| 临时表溢写 | 连接级调大 `tmp_table_size` | 37.4s → 2.1s |
| 错误执行计划 | 移除未被使用的索引 | 40.9s → 2.1s |
| 扫描量过大 | 默认视图走预计算表 | 26.7s → 0.17s |
| 明细排序 | 排序键改为主键（自增与写入顺序一致），避免 16 万行 filesort | 1s+ → 0.5s |

1. **为什么用 `#{}` 不用 `${}`？**

   只有日期范围 → 预计算表（快）；含渠道/类目/省份 → 回明细即席聚合（准）。
3. **为什么明细下钻要用物理分页而不是内存分页？**
   内存分页是"查出全部 16 万行再截取 10 行"，网络传输和内存都浪费；
   物理分页用 SQL 的 `LIMIT offset, size`，数据库只返回需要的行。
</details>

## 7. 前端可视化（Vue3 + ECharts）

### 7.1 🔧 三个关键设计

**① 图表容器组件封装**：把初始化、更新、`resize`、`dispose` 收敛到一个组件，业务视图只提供 `option`。

```vue
<!-- 业务代码只关心 option，不用管生命周期 -->
<ChartBox :option="trendOption" height="340px" />
```

**不封装会怎样**：每个图都写一遍 `echarts.init` / `setOption` / `window.onresize` / `dispose`，
漏掉 `dispose` 还会内存泄漏（切换页面后旧实例仍占内存）。

**② 一处筛选、全部联动**：

```javascript
// 筛选条件统一管理 → 改一次，8 个接口用同一份参数并行请求
const query = reactive({ startDate, endDate, channel, categoryId, province, payType })

async function loadAll() {
  const [overview, trend, category, product, channel, paytype, region, chCat]
      = await Promise.all([...])   // 并行，不是串行 await
  // 分别塞进各自图表
}
```

`Promise.all` 并行请求，总耗时 = 最慢那个接口；如果串行 `await`，总耗时 = 8 个相加。

**③ 前端做数据整形（交叉表转分组柱状图）**：
后端返回的是扁平的 `(渠道, 类目, GMV)` 列表，ECharts 分组柱状图需要"x 轴数组 + 多个 series"，
这个转换放在前端做更合适（后端保持接口语义单纯）。

```javascript
// [(渠道, 类目, gmv)] → { categories: [...], series: [{name:'APP商城', data:[...]}, ...] }
```

### 7.2 ❓ 自查

1. **为什么后端不直接返回 ECharts 需要的格式？**
   后端接口应该面向"业务语义"（渠道×类目的 GMV），而不是某个具体图表库的数据结构。
   如果后端迁就 ECharts，以后换图表库就得改后端。
2. **`Promise.all` 和 `for + await` 有什么区别？**
   前者并行发起，总耗时取决于最慢的那个；后者串行，总耗时是所有请求之和。

## 8. 工程化与部署

### 8.1 Maven 多模块结构

```
spark-sales-analysis (parent, pom 打包)
├── spark-job   → 离线计算，打成可提交给 Spark 的 jar
└── server      → Web 服务，打成可执行的 Spring Boot jar
```

**为什么要多模块而不是一个大工程？**
两个模块的**运行环境完全不同**（一个是批处理提交到集群，一个是常驻 Web 服务），
依赖也不同。分开后：`spark-job` 依赖 Spark，`server` 完全不依赖 Spark —— 部署时各取所需。

### 8.2 一个必须理解的坑：集群提交包从 112MB 降到 1MB

**问题**：`spark-sql` 是 compile 作用域，它的传递依赖除了 `org.apache.spark:*`，
还有 parquet / orc / arrow / netty / avro / zookeeper 等几十个包。
最初用"**排除 Apache Spark**"的黑名单打包，结果漏进来 **112MB**。

**为什么这是问题**：这些包 Spark 自带的 `${SPARK_HOME}/jars` 里**全都有**，
打进提交包会造成**同一个类的两个版本同时存在** → 典型症状是运行时报 `NoSuchMethodError`。

**解决**：改用 shade 插件的 `<includes>` **白名单**，只打包"本项目代码 + MySQL 驱动"：

```xml
<artifactSet>
  <includes>
    <include>com.sales:spark-job</include>
    <include>mysql:mysql-connector-java</include>
  </includes>
</artifactSet>
```

**效果**：112 MB → **1.04 MB**，并且实测用这个精简包跑通了完整作业（结果与全量包逐位一致）。

> **这个案例的价值**：它说明你理解"**依赖边界**"—— 哪些东西该由自己的包提供，哪些该由运行环境提供。
> 黑名单 vs 白名单的选择，本质是"我不知道会漏什么" vs "我只知道自己要什么"。

### 8.3 两种运行环境（一份代码）

| | Windows 单机 | Linux 集群 |
| --- | --- | --- |
| Spark 模式 | `local[*]` | `local[*]`（推荐）或 YARN |
| 数据源 | 本地 `data/raw` | HDFS `hdfs://.../sales/raw` |
| 结果库 | 本机 MySQL | 宿主机 MySQL（`192.168.10.1`） |
| 提交方式 | `java -cp ...` | `spark-submit` |
| winutils | **需要**（Windows 特有） | 不需要 |

**切换只需要改配置，一行代码都不用动**：

```properties
spark.master=                          # 留空 = 交给 spark-submit 决定
data.raw.dir=hdfs://192.168.10.128:8020/sales/raw
jdbc.url=jdbc:mysql://192.168.10.1:3306/sales_analysis?...
hadoop.home.dir=                       # Linux 留空
```

### 8.4 ⭐ 配置加载的优先级（一个真实的坑）

**问题**：`--master local[*]` 时 `spark.driver.extraJavaOptions` **不生效**
（因为 local 模式下 Driver 就是 spark-submit 启动的那个 JVM，没有独立的 Driver 进程），
所以用 `-Dconfig.file=xxx` 指定外部配置**会静默失效**，作业用 jar 里内置的默认配置。

**解决**：让程序**从当前工作目录读取同名配置文件**，优先级设计成：

```
① jar 内置（默认值，保证任何环境都能跑起来）
   ↓ 覆盖
② 工作目录 ./spark-job.properties（集群上改配置不改 jar）
   ↓ 覆盖
③ -Dconfig.file=xxx（显式指定，cluster 模式用）
   ↓ 覆盖
④ -Dkey=value（最高优先级，临时覆盖单个参数）
```

并且启动时打印生效配置，一眼能看出配置有没有生效：

```
[JobConfig] 已加载工作目录配置：/home/hadoop/spark-sales-analysis/spark-job.properties
[JobConfig] 生效配置 -> spark.master=local[*] | data.raw.dir=hdfs://... | jdbc.url=... | jdbc.password=<已设置>
```

> **这个设计体现的思路**：不是"让用户改对了才工作"，而是"**让错误的配置无法静默生效**"。
> 好的工程实践是把"容易犯的错"变成"不可能犯的错"，或者"一犯就能立刻发现"。

### 8.5 ❓ 自查

1. **为什么集群提交包不能包含 Spark 自身？**
   `spark-submit` 会把 `${SPARK_HOME}/jars/*` 加到 classpath，Spark 由集群提供。
   自己的包里再带一份会造成类冲突（版本不一致时报 `NoSuchMethodError`）。
2. **JDK 8 为什么限制 Spring Boot 版本？**
   Spring Boot 3.x 要求 JDK 17+，JDK 8 只能用到 2.7.x（2.7 是最后一个支持 JDK 8 的版本线）。
