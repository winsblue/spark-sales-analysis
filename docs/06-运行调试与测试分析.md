### 2.3 两种计算方式对比测试（提高层要求）

同一份数据、同样的清洗与统计逻辑，分别用 DataFrame 与 RDD 实现：

| 计算方式 | 总耗时 | 清洗耗时 | 统计与落库耗时 | 输入行数 | 输出行数 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| DataFrame / SparkSQL | **36,628 ms** | 12,216 ms | 24,412 ms | 200,177 | 220,108 | SUCCESS |
| RDD | **51,747 ms** | 4,266 ms | 47,481 ms | 200,177 | 220,108 | SUCCESS |

**结论**：DataFrame 方式比 RDD 方式快 **41.3%**。

- RDD 的**清洗阶段反而更快**（4,266 ms vs 12,216 ms），因为它是一次 map 转换，而 DataFrame 的清洗包含多次 `withColumn`、窗口函数去重与广播 Join；
- 但在**聚合与落库阶段 DataFrame 优势明显**（24,412 ms vs 47,481 ms），Catalyst 优化器与 Tungsten 编码带来的收益在分组聚合场景下体现充分。

> **踩坑记录（重要）**：第一次做对比测试时得到"RDD 比 DataFrame 快"的相反结论。
> 排查后发现 ODS 装载（20 万行入库）只算进了 DataFrame 那一轮，RDD 轮次没做这一步，两者工作量不等价。
> 修正为"ODS 装载作为公共前置步骤、不计入任何一方耗时"后，才得到上面的公平结果。
> 这也说明：**基准测试的结果与预期相反时，应先怀疑测试方法，而不是急着下结论。**

### 4.3 慢查询定位与优化（性能分析）

测试中发现商品排行接口响应超过 30 秒并超时，通过以下步骤定位并解决：

#### 问题 1：`COUNT(DISTINCT)` 临时表溢写磁盘

```
-- 现象：趋势查询与商品排行查询均超过 30 秒
-- 排查：EXPLAIN 显示 Using temporary; Using filesort
-- 查看变量：tmp_table_size = 18,874,368（仅 18 MB）
--          max_heap_table_size = 16,777,216（16 MB）
--          innodb_buffer_pool_size = 44,040,192（42 MB）
```

MySQL 5.5 默认 `tmp_table_size` 仅 18 MB，而 `COUNT(DISTINCT order_id)` 需要在临时表中维护去重集合，
19 万行的去重集合超过该上限后会被迫落盘，导致查询慢十几倍。

**优化措施**：在后端连接池建立物理连接时自动放大会话级临时表上限：

```yaml
spring:
  datasource:
    hikari:
      connection-init-sql: SET SESSION tmp_table_size=134217728, SESSION max_heap_table_size=134217728
```

**优化效果**

| 查询 | 优化前 | 优化后 |
| --- | --- | --- |
| 每日趋势（COUNT DISTINCT order_id） | 37,370 ms | **2,114 ms**（提升 17.7 倍） |
| 商品排行（GROUP BY + COUNT DISTINCT） | 40,930 ms | **2,110 ms**（提升 19.4 倍） |

#### 问题 2：索引导致优化器选择低效执行计划

```
-- EXPLAIN 输出
key = idx_dwd_product     rows = 192,928     Extra = Using where; Using temporary; Using filesort
```

明细表上原本建了 `idx_dwd_product (product_id)` 与 `idx_dwd_user (user_id)` 两个单列索引，
但本项目的查询模式是"按日期范围 + 维度分组聚合"，从不按商品或用户筛选明细。
优化器误选了该二级索引，导致 **19 万次回表查询**，比全表顺序扫描慢十几倍。

**优化措施**：从 DWD 表结构中移除这两个索引。

```sql
-- 修改前
KEY `idx_dwd_product` (`product_id`),
KEY `idx_dwd_user` (`user_id`)
-- 修改后：移除（明细查询不按商品/用户筛选，保留索引反而引入错误执行计划并拖慢写入）
```

> 这是一个典型的"**索引不是越多越好**"案例：未被查询使用的索引既增加写入开销，
> 又可能误导优化器选择回表计划。

#### 问题 3：商品排行扫描量过大

商品排行的分组键包含 `product_name / category_name / brand` 三个长字符串列，
临时表索引长度超过 1 KB，即使调大临时表上限仍可能落盘。

**优化措施**：默认视图（无维度筛选）下的商品排行改从预计算表 `ads_product_stat` 读取，
扫描量由 19 万行降至 1.8 万行；带维度筛选时仍走即席聚合以保证联动正确。

**优化效果**：`/api/product/topn` 由 **26,650 ms 降至 173 ms**（提升 154 倍）。

#### 优化小结

| 优化项 | 手段 | 效果 |
| --- | --- | --- |
| 临时表溢写 | 连接级调大 `tmp_table_size` / `max_heap_table_size` | 趋势查询 37.4s → 2.1s |
| 错误的执行计划 | 移除未被使用的单列索引 | 商品排行 40.9s → 2.1s |
| 扫描量过大 | 商品排行默认走预计算表 | 26.7s → 0.17s |
| 明细排序 | 排序键由 `order_time` 改为主键 `id`（自增与写入顺序一致） | 避免 16 万行 filesort |
