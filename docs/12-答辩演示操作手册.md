## 三、演示脚本（8 分钟，与 `docs/08` 第 13 页配套）

> 建议：PPT 讲到**第 13 页「系统演示」**时切到浏览器。PPT 与操作交替，不要全程念 PPT。

### 第 1 段 · 开场（30 秒）— 浏览器停在 `http://localhost:8080/`

**操作**：什么都不点，让看板完整显示。

**讲**：

> "这是系统的销售分析看板。数据来自 **Olist 巴西电商公开数据集**——10 万笔真实订单，
> 不是模拟数据。整条链路是：CSV → Spark 清洗与多维统计 → MySQL 三层数仓 → Spring Boot 接口 → 这个页面。"

**为什么先强调"真实数据"**：评委最常质疑"数据是自己造的，结论没意义"。先说清数据来源，后面所有数字都可被外部验证。

### 第 2 段 · 指标卡 + 日期筛选（90 秒）— ★核心演示点

**步骤 1**：鼠标划过指标卡，说明 9 项指标。

**讲**：

> "9 项核心指标。注意每张卡右上角的**「预计算」**标签——说明这个数字是从离线作业预先算好的结果表里直接读的，
> 响应很快。这 9 项的口径是统一的：有效订单 = 已完成 + 已支付，GMV 只算有效订单，下单量包含取消和退款。"

**步骤 2**：在筛选条把开始日期改成 `2018-08-01`、结束日期改成 `2018-08-31`，点**「查询」**。

**预期结果**：

| 指标 | 变化 |
| --- | --- |
| 成交金额 | 1349 万 → **848,860.10** |
| 下单量 | 98,666 → **6,452** |
| 下单用户数 | 94,983 → **6,380** |
| 卡片标签 | 「预计算」→ **「即席聚合」** |

**讲**（这段是全场最有说服力的一段）：

> "日期范围一改，所有图表同步刷新。更重要的是**标签从「预计算」变成了「即席聚合」**——
> 这是系统的双路径查询策略：只有日期范围时走预计算表，快；一旦带了维度筛选，
> 预计算表里没有那个维度，就自动改为对明细表做即席聚合，保证筛选联动正确。
> 而且用户数是**在区间内整体去重**的，不是把每天的每日去重数相加——后者会把复购用户重复计数。"

**如果评委追问"怎么保证两条路径口径一致"**：切到监控页看第 4 段的一致性校验。

### 第 4 段 · 运行监控页（90 秒）— 点顶部「运行监控」或访问 `/#/monitor`

页面从上到下 4 块内容，**按这个顺序讲**：

**① 数据质量报告**

当前显示：原始 **102,425** / 有效 102,425 / 丢弃 **0** / 质量得分 **100.00%**。

**讲**（注意：这里必须主动解释，否则会被质疑）：

> "这一页显示丢弃 0 条、质量得分 100%。**这不是因为没做清洗，而是因为这份公开数据集
> 已经被发布方清洗过了**——所以我的 8 条清洗规则几乎没有命中，只命中 1 条空值。
>
> 所以我另准备了一套**注入 8 类脏数据**的模拟数据集来验证清洗规则，稍后切过去看。"

**② 清洗规则命中统计**：6 行规则表（R01~R08 + 处理方式 + 命中数）。继续讲：

> "规则分两类：可修复的（R01 空值填充、R06 金额重算、R07 状态标准化、R08 维度补全）保留记录；
> 不可修复的（R03 时间无法解析、R04 数量非法、R05 单价非法）丢弃并写入留痕表，可以追溯到批次号。"

**③ 计算方式性能对比** ★提高层要求

**预期结果**：两行记录，DATAFRAME 与 RDD，以及一行自动生成的结论。

**讲**：

> "这是提高层要求的'比较不同处理方式'。同一份数据，我分别用 RDD 和 DataFrame/SparkSQL 实现了一遍。
> 在这份真实数据上，DataFrame 快约 1.5%——差距很小，因为瓶颈在写库的 IO，不在计算。
> 而在模拟数据上差距是 24%，这个对比稍后能看到。"

**④ 数据一致性校验**

**预期结果**：4 行校验，**差值全为 0，结果全部「通过」**。

**讲**：

> "这是我自己加的一道保险：把预计算表和明细实时汇总的结果对一遍。
> GMV、销售件数、有效订单量、类目 GMV 四项差值都是 0，说明两条查询路径口径完全一致。
> 用户数这类**不可加指标**不参与逐项比对——因为跨天求和会重复计数，这是口径本身的限制，不是缺陷。"

## 四、四个"必须先知道"的事实（不知道就会被问住）

### ① 真实数据的渠道饼图只有 1 个扇区

**原因**：Olist 公开数据集**没有"销售渠道"字段**。

**话术**：

> "这份数据集没有渠道字段，所以我把它统一映射为'平台自营'。渠道维度在模拟数据集上是完整的 5 个值。
> 如果接入有渠道字段的数据源，这个图表会自动有值——表结构和接口都是通用的。"

**演示建议**：讲渠道时直接讲**支付方式占比**（5 个值，效果好），跳过渠道饼图。

---

### ② 真实数据的退款率、折扣率为 0%

**原因**：Olist 数据里**没有退款金额字段、也没有优惠字段**，无法计算。

**话术**：

> "这两个指标显示 0，不是没有退款，而是**源数据里没有任何字段能证明一笔订单发生了退款**。
> 我选择宁可显示 0，也不去编造数据。这也是我把 `unavailable`（无法履约）映射成独立状态
> 而不是武断地算作退款的原因——**无法从数据证明的结论就不要下**。"

**这是在展示数据严谨性，是加分项，不是缺陷。**

---

### ③ 真实数据的清洗丢弃数是 0

**原因**：公开数据集已被发布方清洗过。

**话术**：见第 4 段②。**要点是主动说、不要等评委问**。

---

### ④ 各类"全部项占比之和"是 100.01%~100.04%

**原因**：百分比四舍五入到 2 位小数的累积舍入误差（74 个类目累加）。

**话术**：

> "各项占比保留 2 位小数，累加会有 0.01~0.04 的舍入误差，属正常现象。"

## 六、高频提问速答（20 问）

| # | 问题 | 一句话回答 |
| --- | --- | --- |
| 1 | 数据从哪来？ | Olist 巴西电商公开数据集，10 万笔真实订单；另有一套注入脏数据的模拟数据用于验证清洗 |
| 2 | 为什么不用 Hive？ | Hive 查询延迟高，不适合后端接口直接查；本项目保留 ODS/DWD/ADS 分层思想，结果落 MySQL 更适合服务化 |
| 3 | 为什么不做实时？ | 属拓展层要求，按教师要求不做。链路预留了扩展点：加 Kafka+Flink 后只需换 ADS 写入方式，接口不用改 |
| 4 | 数据量这么小为什么要用 Spark？ | 项目定位是打通链路；Spark 收益随数据量放大。已用 20 万行验证逻辑，并预留 `--master yarn` 集群提交能力 |
| 5 | 预计算和即席查询口径会不会不一致？ | 会，所以做了 `/api/monitor/consistency` 自动比对，4 项可加指标差值全 0；不可加指标（用户数）不参与比对并说明了原因 |
| 6 | RDD 比 DataFrame 慢，是不是 RDD 写错了？ | 不是。DataFrame 有 Catalyst 优化和 Tungsten 编码，且代码量少一半。这正是结论想说明的：离线分析优先用 DataFrame |
| 7 | 为什么真实数据上两者只差 1.5%？ | 瓶颈在写库 IO，不在计算。模拟数据上差 24%，因为那一套的商品维度基数高、落库数据量大。**IO 是瓶颈时换计算引擎收益有限** |
| 8 | 数据一致性怎么保证？ | 三点：口径集中定义在 `Schemas` 与文档；两种实现共用同一份 DWD；提供自动比对接口 |
| 9 | 项目最大的难点？ | 不是写 Spark 代码，是"把口径想清楚"。例如最初把 TopN 固化进结果表导致筛选不联动，返工重做了 ADS 层 |
| 10 | 排名和占比为什么要后端算？ | 固化进结果表后，前端切换日期范围排行榜不会变，筛选就不联动了 |
| 11 | 用户数为什么不能跨天相加？ | 同一用户在多天下单会被重复计数。所以区间查询时是**整体去重**，不是累加每日去重值 |
| 12 | 清洗丢弃的数据去哪了？ | 写入异常留痕表 `dwd_clean_reject`，含批次号、规则编号、原因，可追溯到原始记录 |
| 13 | 作业重复跑会不会数据翻倍？ | 不会。每次落库前先 `TRUNCATE` 再写，保证幂等；每次运行生成独立 `batch_id` |
| 14 | 你做了哪些性能优化？ | 三个真实定位的问题：① MySQL 5.5 `tmp_table_size` 仅 18MB 导致去重临时表溢写磁盘，趋势查询 37.4s→2.1s；② 冗余索引 `idx_dwd_product` 让优化器误选二级索引造成 19 万次回表，商品排行 40.9s→2.1s；③ 商品排行改走预计算表，26.7s→173ms |
| 15 | 怎么发现性能问题的？ | 先看现象拆解耗时，再用 `EXPLAIN` 看执行计划，最后用对照实验验证（换索引、调参数各测一遍） |
| 16 | 退款率为什么是 0？ | 源数据没有退款金额/时间字段，无法证明。宁可显示 0 也不编造（详见第四节②） |
| 17 | 渠道为什么只有一个值？ | Olist 数据集没有渠道字段（详见第四节①） |
| 18 | 如果数据涨到 1 亿行？ | 单机顶不住，需切 YARN 集群；同时处理数据倾斜（按类目/日期加盐）、调整分区数、ADS 改预聚合宽表 |
| 19 | 这个项目你独立完成的吗？ | 可以讲分工：需求与口径设计、数仓分层与清洗规则、Spark 双实现与性能对比、后端接口与前端看板 |
| 20 | 还能怎么改进？ | ① 引入调度（Airflow/Quartz）定时跑作业；② 加 Redis 缓存热点查询；③ 接入实时链路；④ 完善权限与多租户 |

## 七、应急预案

### 7.1 服务启动失败

```powershell
powershell -ExecutionPolicy Bypass -File scripts\demo-stop.ps1   # 先清干净
powershell -ExecutionPolicy Bypass -File scripts\demo-start.ps1  # 再启动
```

还不行就看日志：`logs\demo-8080.log` / `logs\demo-8080.err.log`。

| 报错 | 原因 | 解决 |
| --- | --- | --- |
| `port 8080 is already in use` | 端口被占 | 先跑 `demo-stop.ps1` |
| `Access denied for user 'root'` | MySQL 口令不对 | 检查 MySQL 是否运行、口令是否为 `123456` |
| `Communications link failure` | MySQL 没启动 | 启动 MySQL 服务 |
| `backend jar not found` | jar 没构建 | `mvn -f pom.xml -pl server -am clean package -DskipTests` |

### 7.2 页面打开是空白 / 显示"未查询到数据"
